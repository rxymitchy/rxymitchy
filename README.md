## What I work on

I build software that sits next to a real decision: is this answer true in this language, should this credit file move, what work in a business still depends on one person.

- **Agents and evaluation.** [Taska](https://github.com/rxymitchy/taska) checks whether AI answers hold up for African languages and local context, then records payment for the people who did the check. [Kredoof](https://github.com/rxymitchy/Kredoof) scores credit from verified on-chain activity.
- **Products in TypeScript.** Next.js, React, and Postgres for the parts a person actually uses: auth, roles, and a status you can trust.
- **Python services and models.** [Northline](https://github.com/rxymitchy/northline) reads how a business works and says what is still manual. Separate from that, notebooks and small models for loan eligibility and whether land can take more development, plus reinforcement-learning agents that play games under prospect theory.

## Open it, then maintain it

A private repo nobody else can run is a demo. Open source is the practice of leaving the door unlocked and still being there when someone walks in.

If you are about to publish something:

1. Say what it does in the first five lines.
2. Write the exact commands to run it.
3. Add a license.
4. Leave one issue a new person can finish in an evening.

If you want to practice maintaining, start on code that already has users in mind:

- [Northline](https://github.com/rxymitchy/northline) is MIT-licensed and has a [contributing guide](https://github.com/rxymitchy/northline/blob/master/CONTRIBUTING.md). Open an issue or a small pull request.
- [Taska](https://github.com/rxymitchy/taska) and [Kredoof](https://github.com/rxymitchy/Kredoof) are public. Read the README, then change one thing and say what you checked.

A useful pull request is small, matches the style already in the file, and leaves the project easier to run than you found it. Maintenance is the part that makes the license mean something.
